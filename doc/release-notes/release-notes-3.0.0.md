# Radiant Core 3.0.0 Release Notes

**Release Date**: May 2026
**Release Type**: Wallet & security hardening (non-consensus)
**Hard Fork Activation**: None — the V2 fork at block 410,000 (introduced in v2.0.1 / v2.1.0) remains the latest consensus change
**Git Tag**: v3.0.0

> **Note**: 3.0.0 is **not** a mandatory consensus upgrade. Nodes already running a recent 2.x release will remain on the main chain. However, wallet operators, exchanges, and integrators **should upgrade** because the default HD derivation path changes (see "Wallet compatibility" below).

---

## Overview

Radiant Core 3.0.0 is a wallet and release-engineering hardening release. It introduces Radiant's registered BIP44 / SLIP-0044 derivation path as the default for new HD wallets, tightens BIP39 mnemonic validation, locks down the GUI auto-downloader against DNS-rebinding and CSRF, and fixes two correctness issues in the BLAKE3 / K12 crypto implementations introduced in 2.1.0.

### What's new in 3.0.0

- **BIP44 SLIP-0044 derivation** — new default path `m/44'/512'/0'/0/k` (`512` is Radiant's registered SLIP-0044 coin type)
- **Legacy derivation preserved** — `WALLET_FLAG_LEGACY_DERIVATION`, `-derivationtype=radiant|legacy`, and a `legacy_derivation` parameter on `createwallet`
- **Strict BIP39 checksum** — `validate_mnemonic()` defaults to `strict_checksum=True`
- **GUI auto-downloader hardening** — per-launch CSRF token, Host header validation, mandatory SHA-256 verification of downloaded artifacts
- **BLAKE3 counter fix** — now uses the chunk counter, not the block counter (test vectors > 1024 bytes now pass)
- **Input length limits** on BLAKE3 and K12 hashers
- **Release process** — `RELEASE_SECURITY_PROCESS.md` documents signed-tag / dual-maintainer-signature / signed-checksum requirements

## Wallet compatibility

| Wallet state | Behavior in 3.0.0 |
|--------------|-------------------|
| **Existing 2.x wallet, opened in 3.0.0** | Keeps its original derivation path. The `WALLET_FLAG_LEGACY_DERIVATION` is recorded on first open if the wallet was created pre-3.0.0. No address changes. |
| **New wallet created in 3.0.0 (default)** | Uses `m/44'/512'/0'/0/k`. Addresses are not interchangeable with a legacy wallet's addresses for the same seed. |
| **New wallet created in 3.0.0 with `-derivationtype=legacy`** | Uses the previous derivation path. Use this only for interop with legacy tooling that hasn't been updated. |
| **`createwallet` RPC** | Accepts a new `legacy_derivation` boolean; defaults to `false` (Radiant SLIP-0044). |

> **Important for integrators**: If you restore a seed phrase that was generated by a 2.x wallet into a fresh 3.0.0 wallet without `-derivationtype=legacy`, the resulting addresses will differ from the original. Always restore with `legacy_derivation=true` when bringing forward a pre-3.0.0 seed.

## Security changes

### BIP39 strict checksum

`gui/bip39.py` — `validate_mnemonic()` now defaults `strict_checksum=True`. Mnemonics with invalid BIP39 checksums are rejected outright in the GUI wallet creation / restore flow.

### GUI auto-downloader hardening (`gui/radiant_node_web.py`)

- **Per-launch CSRF token** (`_SECURITY_TOKEN`) — a random token is generated at process start. All API endpoints require the `X-Radiant-Token` header; requests without it are rejected. The token is injected into the local web UI; remote callers cannot forge it.
- **Host header validation** — only `localhost` / `127.0.0.1` Host headers are accepted, preventing DNS-rebinding attacks against the local HTTP server.
- **SHA-256 verification on download** — release assets are downloaded only if the SHA-256 in the bundled `RELEASE_ASSETS` manifest matches the file. Placeholder hashes (`PLACEHOLDER_SHA256_UPDATE_AT_RELEASE`) cause the GUI to refuse the download; maintainers must update the manifest as part of each release.
- **`GITHUB_RELEASE_URL`** now points at the `v3.0.0` release.

### Crypto correctness

- **BLAKE3 counter** (`src/crypto/blake3.cpp`) — fixed to use the per-chunk counter rather than the per-block counter. Inputs larger than one 1024-byte chunk now hash correctly.
- **BLAKE3 / K12 input length limits** (`src/crypto/k12.{cpp,h}`) — both hashers now track input length and reject inputs above the documented maximum, preventing pathological scripts from accumulating unbounded state in the script interpreter.
- **Interpreter check** (`src/script/interpreter.cpp`) — additional guard on hash opcode inputs to align with the new hasher limits.

### Release engineering

`RELEASE_SECURITY_PROCESS.md` documents the release-engineering rules audited under finding C5:

- GPG-signed annotated tags (`git tag -s`)
- Two-maintainer signatures on `SHA256SUMS.txt`
- GUI hash manifest must be updated from placeholders before release
- No binaries committed to the git repo — release artifacts live in GitHub Releases
- Reproducible builds remain a planned future goal

## RPC changes

### `createwallet`

```
createwallet "wallet_name" ( disable_private_keys blank "passphrase" avoid_reuse descriptors load_on_startup external_signer legacy_derivation )
```

- New optional `legacy_derivation` boolean (default `false`). Set to `true` to create a wallet that uses the pre-3.0.0 derivation path.

### Startup flag

- `-derivationtype=radiant|legacy` — sets the default for new wallets created during the current node run. The per-wallet flag stored on the wallet still wins on subsequent opens.

## Upgrade instructions

Same procedure as 2.x — replace the binary, restart the node. Wallets created before 3.0.0 retain their derivation path automatically.

### For exchanges / custodians

- **No consensus action required.** 3.0.0 is wire-compatible with 2.x.
- If you derive addresses from stored seeds (rather than from existing wallet files), confirm whether you want the new BIP44 path or the legacy one, and set `legacy_derivation` on `createwallet` accordingly.

### For wallet integrators

- Update any code that assumes the legacy derivation path. The Radiant SLIP-0044 coin type is `512`; the full BIP44 path is `m/44'/512'/0'/0/k`.
- The `BIP44_COIN_TYPE` constant in `gui/radiant_node_web.py` is now `512` (was `0`).

### For miners

- No action required. No consensus changes.

## Replay protection

Unchanged. Strong replay protection via `SIGHASH_FORKID` continues; no additional protection needed for this release.

---

## Known limitations

- **GUI release-asset manifest** (`gui/radiant_node_web.py:RELEASE_ASSETS`) ships with placeholder SHA-256 values. These **must** be updated to the real per-platform hashes as part of the release build step, per `RELEASE_SECURITY_PROCESS.md` §3. The GUI auto-downloader refuses to install assets with placeholder hashes — this is by design.
- **Reproducible builds** remain a future goal; current release artifacts are built with system toolchains, not `depends/`.
